# hiveplotlib

> **This is the main hub of research and software development for this wiki.**

hiveplotlib is a Python library for generating and visualizing static [[hive-plot|hive plots]]. Created and maintained by Gary Koplik. It is the most comprehensive open-source implementation of Martin Krzywinski's hive plot method.

## Status

- **Current version:** 0.28.0 (released 2026-06-18), focused on streamlined NetworkX integration (see "NetworkX integration" below; the design decisions are distilled in [[0001-networkx-integration|ADR 0001]]). v0.29.0 is accumulating, but none of it has landed: every piece of it sits on an unmerged branch (see "Review queue" below).
- **Python support:** 3.10+
- **Repository:** GitLab — `gitlab.com/hiveplotlib` group (migrated to its own group in the v0.28 cycle; visibility not re-verified from the working tree)
- **Install:** `pip install hiveplotlib`
- **License:** see repo
- **Packaging (committed to branch `53` on 2026-08-02 as `ee6ac5a`, ships with MR !36's merge + immediate v0.29.0 release):** developer-only dependencies moved from published extras to a PEP 735 `[dependency-groups]` table in `pyproject.toml`. The six dev groups (`dev`, `docs`, `testing`, `perf`, `ruff`, `ty`) install only from a source checkout via `pip install --group <name>` (pip >= 25.1) or uv, and no longer appear in published PyPI metadata (wheel-metadata witness: no dev names in `Provides-Extra`), so `pip install hiveplotlib[dev]`-style installs from PyPI stop existing (CHANGELOG names the loss and the `pip install -e . --group <name>` replacement). The six user-facing backend extras (`bokeh`, `datashader`, `holoviews`, `networkx`, `plotly`, `polars`) remain the published extras surface, unchanged; end users are unaffected. Backend-extra coupling survives via `hiveplotlib[<extra>]` package-spec self-references inside the `dev`/`perf` groups (PEP 735 `include-group` cannot reference extras). Every consumer swept to the `--group` forms: `install.sh`/Makefile, GitLab CI (the weekly released-code jobs install the package from PyPI, then the `testing` group from the checked-out tag's tree), Read the Docs (`build.jobs.install` steps), and CONTRIBUTING (pip >= 25.1-or-uv floor noted). `uv audit` was verified to cover dependency groups by default, so the security-audit surface did not narrow.
- **Docs discoverability, investigated and consciously declined (2026-07-18):** the canonical docs are `hiveplotlib.readthedocs.io/stable/` (correctly serving v0.28), but the pre-migration GitLab Pages domain `geomdata.gitlab.io/hiveplotlib` still ranks first in web search for the library's name. Since the v0.28-cycle project transfer, that domain answers with a 302 chain (`projects.gitlab.io/auth` → `gitlab.com/oauth/authorize` → `gitlab.com/users/sign_in` → 403), so the top organic result is an auth-walled dead end and the next several are stale v0.25 through v0.27 pages. Diagnosis: the old address holds years of accumulated inbound links, and a redirect-to-login reads to search engines as "temporarily unavailable" rather than "moved," so the ranking neither transfers nor clears quickly.

  Everything forward-looking is already correct and needs no work: `pyproject` publishes `Documentation = https://hiveplotlib.readthedocs.io/stable/`, the merged NetworkX drawing-docs PR points every link at readthedocs, and the repo carries no stray `geomdata` URLs (the one CHANGELOG mention is a deliberate historical record of the move).

  **Decision: not pursued.** Recovering the accumulated ranking would mean publishing a 301 redirect from the old address, which requires standing up a placeholder project inside the `geomdata` group. The maintainer holds Maintainer access there and the group permits it, but declined the hoops for a group he no longer wants to operate in, judging the docs' search placement low-stakes relative to the effort. Accepted cost: the old domain's link equity is lost rather than transferred, and the dead top result likely persists for months before search engines drop an address they can no longer crawl. Two smaller levers were surfaced and also deferred, both independent of the `geomdata` question: hiding stale/prerelease versions on Read the Docs (`v0.25.1`, `0.26.0b0`, `0.27.0a0` are indexed), and setting `html_baseurl` from `READTHEDOCS_CANONICAL_URL` in `conf.py` to emit per-version canonical links (`import os` is not currently imported there). **Revival trigger:** the JOSS submission landing, which makes the canonical docs URL a cited artifact and raises the stakes on what a reader hits first.

## Core API

### Data Structures
- **`Node`** / **`NodeCollection`** — Individual nodes and pandas-backed collections with partition logic
- **`Edges`** — Tagged edge container supporting multiple edge types
- **`Axis`** — Polar coordinate axis with start/end, angle, node placements

### Main Classes
- **`BaseHivePlot`** — Low-level construction (manual axes, node placement, edge connection)
- **`HivePlot`** — High-level interface (partition → sort → build → plot); also carries the post-0.28 `subset()` derived-plot operation and the persistent `add_highlight` overlay registry (see Key Features)
- **`HivePlotMatrix`** — Comparative grid of hive plots, new in v0.27 (see [[hive-plot-matrix]])
- **`P2CP`** — [[p2cp|Polar Parallel Coordinates]] for tabular data

### Visualization Backends
Six backends: matplotlib (default), bokeh, holoviews-bokeh, holoviews-matplotlib, plotly, datashader.

On `master` (post-0.28, unreleased), the `hiveplotlib[holoviews]` extra now requires `holoviews>=1.23` (was `>=1.15`). That release ships the upstream fix for [holoviews #6469](https://github.com/holoviz/holoviews/issues/6469), which let the library drop an internal workaround that had been forcing the single-color case on the holoviews-bokeh back end through `cmap`. Behavior of single-color edges is unchanged; the version floor moves and the hack is gone (GitLab #30, merged 2026-06-26).

### NetworkX integration (v0.28, shipped)

v0.28.0 makes a NetworkX graph a first-class input and output, removing the manual extract-and-merge boilerplate that earlier workflows needed. The combined design rationale (including the declined `from_networkx` classmethod and the deferred future-igraph questions) is recorded in [[0001-networkx-integration|ADR 0001]]:

- **Build from a graph:** `HivePlot(graph=...)` and `HivePlotMatrix.from_partition(graph=...)` / `from_variable_sweep(graph=...)` accept a NetworkX graph directly instead of separate `nodes` / `edges`. `graph_directed` / `graph_multigraph` default off `graph.is_directed()` / `graph.is_multigraph()`, so directed and multigraph inputs flow through without restating the type. (`from_tags` is intentionally excluded: tags are an `Edges`-level concept.)
- **Export to a graph:** `HivePlot.to_networkx()` (and the underlying `converters.nodes_edges_to_networkx()`) round-trip a hive plot back to any of the four NetworkX graph classes; multi-tag `Edges` get a `tag` edge attribute.
- **Graph metrics on construction:** `node_graph_metrics` / `edge_graph_metrics` (plus `*_graph_metric_kwargs` / `*_graph_metric_rename`) compute and attach metric columns *before* partitioning, so they are immediately usable as `partition_variable` / `sorting_variables`. `compute_graph_metrics()` does the same for existing `HivePlot` / `HivePlotMatrix` instances. When you build from `nodes` / `edges` and leave `graph_directed` unset, the internal graph's directedness is inferred from the requested metrics (asking for `triangles` builds an undirected graph; `in_degree` builds a directed one), and a contradictory request raises an up-front `ValueError` instead of silently picking a side. A simple-graph build that collapses same-direction duplicate edges now warns by default (`warn_on_parallel_edge_collapse`). See [[graph-features]] for the full graph-type-handling rules.
- **Backend dispatch for graph metrics:** a `graph_metric_backend` parameter on `compute_graph_metrics()`, `HivePlot`, and all five `HivePlotMatrix` surfaces (including the `from_*` classmethods) routes metric computation through NetworkX's backend dispatch system (nx-parallel tested in CI; nx-cugraph known-good but GPU-only). Unknown or uninstalled backend names raise `InvalidGraphMetricBackendError` up front; metrics a backend does not implement fall back to default NetworkX with an INFO log line (the codebase's first use of stdlib logging). A per-metric reserved `"backend"` key in the metric-kwargs dicts overrides the global value, with explicit `None` as the per-metric opt-out; precedence runs per-metric > per-call > stored construction value, mirroring `graph_directed`. This is orthogonal to the future igraph wrapper-library axis (see [[graph-features]] for the three distinct "backend" senses). New gallery notebook: Graph Metric Backends.
- Removed the long-deprecated `hive_plot_n_axes()` (folded into `HivePlot` back in v0.26).

### Performance regression + equivalence harness (shipped 2026-07-03, dev/CI infrastructure)

In place as of 2026-07-03 (GitLab #52; no user-facing API change, not tied to a release): the gate for the upcoming scaling-to-larger-networks milestone. Every scaling workstream must prove "measurably faster (or no worse), output-equivalent to the baseline single-shot datashader path, no regression on small graphs" through it before claiming the win. Design decisions distilled in [[0002-performance-regression-harness|ADR 0002]]; key facts:

**Vocabulary note (committed 2026-08-09 as `8fd4908`):** the harness's reference side was renamed from "proven" to "baseline" throughout `runners/performance/` and its tests, including the public `assert_raster_equivalent(proven_kwargs=...)` keyword, which is now `baseline_kwargs=`. This page follows the code. [[0002-performance-regression-harness|ADR 0002]] still says "proven" and is deliberately left alone: accepted ADRs are append-only, and this is a wording change, not a decision change.

- **Pytest ratio gates + ASV history hybrid** — per-MR CI pass/fail is pytest asserting relative, same-run ratios (absolute timings never gate, so the setup survives CI-runner migration by construction); ASV owns timing/memory history and the rolling baseline, its native results JSON committed as-is.
- **Equivalence wall** — dtype-aware curve + raster comparison against the baseline path, sound by construction (identity must pass, perturbation must fail, comparing-nothing raises).
- **Two-tier peak-RSS measurement** — tier 1 exact kernel high-water mark (child-reported `getrusage(RUSAGE_SELF)` via a two-level subprocess; `tracemalloc` rejected as blind to numba/numpy C allocations); tier 2 psutil-sampled process-tree helper, provisional pending the scaling chain's instrument selection.
- **Capture-at-merge on the designated machine** — ASV history written only by maintainer-local runs (machine tag `ringtail`) at workstream and dependency-bump merges; CI never writes history.

### Scaling to larger networks (shipped to branch `53`, v0.29.0, unreleased)

The five-workstream scaling milestone the harness above was built to gate has now landed end to end on branch `53-scale-hiveplotlib-to-larger-networks` (MR !36, `Closes #53`, targets v0.29.0, unreleased; stress-tested against a 62M-edge OGB network). Each workstream cleared the equivalence wall (byte-identical output to the baseline single-shot datashader path) before claiming its win. The five pieces:

- **Scale-adaptive integer membership indices (WS1):** `Edges.relevant_edges` now stores each axis pair's edge membership as an integer array of edge-dataframe row positions instead of a full-length boolean mask, so a sparse selection no longer carries an all-edges-wide array. Anyone reading `relevant_edges` directly must now apply the stored positions positionally (`df.iloc[positions]`). All built-in backends and `HivePlot.to_json` produce identical output. This is the single representation-agnostic seam the `edge_coverage` property was written behind.
- **Streamed datashader rasterization (WS2):** the three `datashade_*_mpl` entry points take a `stream_chunk_threshold` parameter; chunked rendering kicks in automatically at 1,000,000+ edges or nodes, leaves the rendered figure unchanged, and bounds peak render memory by the largest chunk rather than the whole network. Non-chunkable reductions (`ds.var()`, `ds.std()`) ignore the threshold.
- **Rasterize from stored edge ids without persisting curves (WS3):** the datashader entry points can now rasterize straight from stored edge ids. Edge subsets whose curves were never constructed (`add_edge_ids()` without `construct_curves()`) are built during rasterization and immediately discarded, never persisted, so with streaming the peak resident curve memory is bounded by the largest (axis pair, tag) chunk. The other four backends still require `construct_curves()` and now warn (instead of silently drawing an edge-less figure) when a subset holds edge ids but no curves, naming `construct_curves` and the datashader alternative.
- **narwhals input boundary (WS4):** `NodeCollection` and `Edges` accept any eager narwhals-supported dataframe (`polars`, `pyarrow`, `modin`, `cuDF`, alongside `pandas`), dispatch operations to the user's own library pass-through, and return `data` in that same library (round-trip contract; ndarray edge input is the one exception, which becomes pandas). Both classes gain a `frame_library` property and a `to_pandas()` method. `narwhals` joins the core dependencies on purpose (pure-Python, single `py3-none-any` wheel, no compiled paths); making it optional would fork the code path. Internal derived tables (axis placements, geometry, rasterization) stay pandas/numpy. Design detail lives in the `frames.py` architecture note. **Follow-on, 2026-08-02 (`1700c5f`):** `polars` became a CI-exercised backend rather than one only covered inside the full dev install. The `polars` extra gained `pyarrow` (polars defers to pyarrow for `to_pandas()`), `polars` joined the `base_installs` add-on matrix so the extra is installed and tested in isolation, and roughly 335 lines of polars-parametrized cases moved out of `edges_test.py` / `node_test.py` into `polars_test.py`. `frames_test.py` dropped its module-level `pytestmark` so no test carries both `unmarked` and `polars`, which is what kept polars cases out of a base install's `-m unmarked` run.
- **Dask and cuDF passthrough (WS5):** lazy `dask.dataframe` edge frames flow through the same boundary with no extra parameters and stay lazy end to end (non-materialized edge membership; the datashader backend rasterizes partition by partition through datashader's own Dask pipeline, including `ds.var` / `ds.std`), and `cuDF` frames rasterize on the GPU through datashader's CUDA path. Dask ships with `hiveplotlib[datashader]`. Two follow-on CI-only fixes forced the serial Bézier kernel and avoided concurrent arrow string `Index` construction on the Dask route (thread-safety, not behavior).

Three new gallery notebooks accompany the milestone: Creating Hive Plots from Polars, from Dask, from cuDF. This landed input boundary is what the [[hiveplotlib|subset/highlight faithful-lazy posture]] and the [[0002-performance-regression-harness|equivalence wall]] both build on.

**Added after the five (Workstream 8, committed 2026-08-18 as `2ad1916`):** render-time curve geometry on the datashader edge entry points, plus the fix for a defect the milestone surfaced.

- **The defect.** `construct_curves()`, `connect_axes()`, and `add_edge_curves_between_axes()` all hardcoded `num_steps=100` and ignored the instance's `num_steps_per_edge`, so through v0.28 curves built via those three came back at 100 no matter what the constructor was told. All three now default `num_steps` to `None` and resolve it against the instance attribute. This is the one user-visible behavior change in the workstream, and it carries a `Changed` CHANGELOG entry.
- **The new lever.** `datashade_edges_mpl()` and `datashade_hive_plot_mpl()` gained `num_steps` and `construct_curves_kwargs` (`short_arc`, `control_rho_scale`, `control_angle_shift`). Either one builds every rendered chunk at the requested geometry for that call alone: nothing is persisted, and curves already on the instance are read past rather than rewritten. `datashade_nodes_mpl` is untouched (nodes have no curves). Off-list keys raise the new `InvalidConstructCurvesKwargError` at the entry point, before any figure, canvas, or Dask computation, so a bad key does not surface as a partition-sizing error from inside the lazy route.
- **Why it exists.** WS3's never-persist route made curve geometry a render-time input, but the only way to lower the sampling rate was `construct_curves()`, which persists every curve and hands back exactly the resident cost the fused route exists to remove. The stated carve-out is in both docstrings: the render-time lever recovers resident memory only where curves are never persisted (lazy input, or an ids-only assembly), and *raises* peak memory on a curve-persisted instance, where `num_steps_per_edge` at construction is the real lever.
- **Lazy drop-site warning.** Lazy (Dask) edge subsets never persist curves, so curve geometry passed to `connect_axes()` for one has nothing to build. That call now warns and names the levers that do apply rather than dropping the request silently. The trigger is value-based, not presence-based, so `connect_adjacent_axes`'s own forwards never fire it and the Dask suite stays clean under `filterwarnings = error`.
- **Resolution home.** A new private `_DEFAULT_NUM_STEPS_PER_EDGE = 100` in `hiveplot.py` is the library's single named construction default, and `num_steps_per_edge` is now a public attribute always present on `BaseHivePlot` (`HivePlot` overwrites it from its constructor parameter). This is the anti-drift seam the [[hiveplotlib|lower-default-curve-resolution plan]] needs, and a test pins the constructor's signature default equal to the constant.
- **P2CP declares its rate too (2026-08-17, closing last week's open must-fix).** `P2CP.build_edges(num_steps=...)` now assigns that rate to the underlying `BaseHivePlot`'s `num_steps_per_edge`, exactly as `HivePlot.__init__` does with its own parameter, so a P2CP built at 16 and rendered with `construct_curves_kwargs` alone rebuilds at 16 rather than at 100. The false docstring clause that provoked the must-fix (that a rebuild takes the *construction* defaults for every geometry field the call omits, `num_steps` included) is gone; the two fallbacks are now stated separately, since the three geometry keys do fall back to construction defaults while `num_steps` falls back to the instance attribute. The curve-geometry model, previously restated across six parameter descriptions, was consolidated into one `.. note::` per function.

**Workstream 9 (`persist_curves`, committed 2026-08-20 as `8966c4d`, refined by `60dc7d1` and `3b8d0d6`):** the never-persist route becomes reachable from the high-level API. Last week's parked emergent finding was that `HivePlot.__init__` ends in an unconditional `connect_adjacent_axes()` with no way to defer it, so WS3's fused route, whose entire value is *not* persisting curve geometry, was reachable for in-memory input only through manual `BaseHivePlot` assembly. It is now a flag.

- **The surface.** `persist_curves` is a `HivePlot` constructor parameter, a parameter on all three `HivePlotMatrix` builders, and a `BaseHivePlot` attribute every rebuild honors. `False` keeps a large network's curve geometry out of resident memory, storing the edge ids and edge keyword arguments the datashader backend rasterizes from; `True` remains the default. `BaseHivePlot.set_persist_curves(persist_curves, drop_existing_curves=False)` sets it after construction, and with `drop_existing_curves=True` also frees the curves an instance already holds while keeping its ids and kwargs (it reuses the traversal `place_nodes_on_axis` already had). `HivePlotMatrix.set_persist_curves` mirrors it, fanning out over every populated cell. The two `bool | None` per-call overrides on `connect_axes` / `connect_adjacent_axes` that the first draft carried were dropped on 2026-08-18: one attribute read, nothing to resolve.
- **Three defects the flag exposed, all fixed on the branch.** `to_json` raised a bare `KeyError: 'curves'` on a subset holding ids without curves and now raises `UnconstructedCurvesError` naming `construct_curves()` (GitLab #63). `update_edges` treated an ids-only subset as absent, warning that it found no edges while silently dropping the requested keyword arguments, which was live for *every* Dask-backed plot since those never persist curves at all; the kwargs half of the gate is now ids-keyed while the geometry-rebuild half stays curve-keyed (GitLab #65). `update_edges` also gained `warn_on_no_edges`, matching `add_edge_kwargs`, so a loop over partition pairs that legitimately have no edges between them stops emitting noise.
- **The memory claim is measured on the `HivePlot` path, not inferred from the hand assembly.** At 100K nodes and 2M edges on the canonical host, `HivePlot(persist_curves=False)` through the fused streamed route peaks at **1.082 GB** against **1.079 GB** for the hand-built ids-only assembly (ratio 1.003, pre-registered ceiling 1.25x) and **5.066 GB** for the two-stage single shot. The 3.2 MB residual is the entire cost of everything the class adds at 100K nodes. The default-persisting counterpart on the same route is 2.340 GB, and a direct probe of the on-instance representation measured float32 at 808.0 bytes per edge exactly, confirming the plan's own arithmetic rather than the 3.2 GB a float64 assumption had predicted.

**Workstream 10 (measurement-confirmation pass, 2026-08-21):** a non-code workstream, added 2026-08-18 on the maintainer's ask, that re-establishes every published number on the tree that will merge. The motivation is that WS2 and WS3 recorded their figures before WS8 shipped and before WS9 existed, so roughly half the sprint's claims were comparisons assembled across a moving tree. Protocol: one session, one host (`ringtail`), six samples per number with the first discarded as warmup and still recorded, each peak-RSS sample its own freshly spawned process, medians and ratios of medians, and a quiet-host rule (no other work on the machine while a child runs).

- **Everything published confirms.** All eight gate constants pass and land inside 10% of their recorded values with no headroom halved; all nine absolute figures confirm inside 4%; the four derived ogbn-products statistics reproduce bit-identically rather than to four significant figures. `make test-performance` ran green in the same session (41 passed, 227 s). No constant was retuned and no figure was edited.
- **One number moved, and it takes the qualified verdict.** The uncapped ogbn run's peak RSS medians 13.560 GiB against a recorded 11.9 (+13.9%), but its five-sample range spans 24.9%, wider than the band itself, so it reads as "outside the band, not attributable" rather than as a regression. This is the first real exercise of that disposition clause.
- **The blog post's thread-cap headline is corrected before publication.** With five samples on both sides, tripling the Dask thread cap from 8 to 24 workers costs **64% more peak memory** (4.202 to 6.892 GiB) and returns no render speedup the samples can detect (64.20 s against 63.98 s, overlapping ranges). The earlier single-sample pair implied 46%.
- **A method finding worth more than the protocol change that prompted it.** The quiet-host rule buys more than the warmup discard: the same configuration spread 13.9% while light verification commands ran alongside it and 3.3% under the rule. Most of what was first diagnosed as scheduler nondeterminism, then as warmup, was contention from the measuring session itself. The discard stays, justified by I/O warmup on the real-data children (first-sample deltas of 5-10%) and demonstrably superfluous on the synthetic ones (at or below 0.49%).
- **Version-to-version, not just route-to-route.** An addendum recovered the before/after claim from the ASV baseline captured 2026-07-03 on the same host, run against the branch tip with `--dry-run` so no history was written. At two million edges the current code rasterizes in **70% of the time using 48% of the memory** (11,173 to 7,850 ms; 5,462 to 2,600 MB) with no user action and no parameter change. Construction also got materially faster at three of four scales, which no workstream claimed and which the streaming and never-persist work does not explain (the membership-storage redesign is the obvious candidate, unverified). Two caveats ride along and are meant to be published with the numbers: rasterizing a 5,000-edge network costs 9 ms and 64 MB more than in July, unattributable from this data since the July environment resolved a different dependency stack; and `time_render_matplotlib` has no July counterpart, so **the default matplotlib backend has no before/after at all**. Every figure here describes the datashader path.

Validation across the three workstreams: full suite **1739 passed, 14 skipped** (cuDF, GPU-gated) at 100% coverage (4,703 statements, 0 missed), `make format` / `make ty` / `make docs` clean at zero Sphinx warnings.

### Key Features
- **`unify_axes` on `HivePlot`** (post-0.28, on branch `51-add-unify-axes-to-hiveplot` / MR !40, unreleased): a `unify_axes` constructor parameter (`HivePlot(..., unify_axes=True)`) plus a post-hoc `HivePlot.unify_axes()` method give every axis the same value range so radial positions are comparable across axes, mirroring the affordance [[hive-plot-matrix|HivePlotMatrix]] already carries. Same `True | {"vmin", "vmax"}` dict / no-arg / one-sided call shapes as HPM (the underlying resolver is now shared code in `_unify_axes.py`); auto-computed `True` unifies within one instance, while the explicit full dict is what lines separate different-data instances up. Extends ADR 0001's HivePlot ↔ HivePlotMatrix symmetry precedent (see [[fixed-layout-comparability]]).
- [[edge-rendering|Edge kwarg hierarchy]] for layered styling
- **Subset and highlight** (on branch `59-subset-highlight` off the scaling branch, MR !43 `Closes #59`, post-0.28, targets v0.29.0, unreleased): two complementary ways to emphasize or restrict to a subgraph without rebuilding a hive plot, deliberately different shapes.
  - **`HivePlot.subset(nodes=, edges=, hops=, closure=)`** returns a new, independent `HivePlot` (copy semantics) with **frozen geometry** — node placements, edge curves, and axis value ranges (`vmin`/`vmax` pinned) identical to the parent, so a drill-down stays comparable against the full plot ([[fixed-layout-comparability|freezing the ranges, not just the placements]], is the load-bearing correctness rule). It is the *induced* subgraph of the selection (NetworkX subgraph/edge_subgraph semantics), locked induced so every kept edge is drawable. It is a cheap slice of already-computed geometry (tested to never call into curve construction) and raises `SubsetBeforeBuildError` if invoked before geometry is built. `HivePlotMatrix.subset(...)` broadcasts the same selection to every populated cell.
  - **Highlight registry** — `add_highlight(...)` / `update_highlight` / `remove_highlight` register named accent state persisting *on* the `HivePlot`, drawn as an **overlay layer above and outside the [[edge-rendering|edge-kwarg hierarchy]]** (the hierarchy's contract is untouched, no new conflict-warning cases). Defaults to `closure="incident"` (the selection radiates: nodes light up plus all touching edges) with an Okabe-Ito colorblind-safe accent palette (first highlight blue `#0072B2`); `induced` is the narrowing option. No auto-dimming of the base (explicitly rejected). Multiple simultaneous highlights, each keyed; one call may combine `nodes=` and `edges=` into one group. The registry lands on `HivePlot`, not `BaseHivePlot`, so `P2CP` does not inherit it. Re-exports a `Highlight` record and `HIGHLIGHT_ACCENT_PALETTE` from the top level (the [[0001-networkx-integration|EdgeCoverage/ADR-0001]] re-export pattern). Overlay renders on matplotlib, bokeh, holoviews, and plotly; `HivePlotMatrix` broadcasts one keyed highlight to every panel with a shared key and color.
  - **Selection vocabulary:** node IDs, boolean mask, narwhals-expression condition shorthand, and (for edges) axis pair or edge mask; `hops` expands the selection as an undirected ego graph (`networkx.ego_graph` semantics; `hops=1` the motivated case). Depends on the narwhals input boundary (see below).
  - **Datashader raises, by design:** registered highlights on any of the three `datashade_*_mpl` entry points raise `HighlightsUnsupportedByDatashaderError` (an accent overlay washes out at datashader density), and the message points at the documented equivalents — `subset(...)` to datashade a drill-down, a non-datashader backend for the overlay, or `remove_highlight()` for the plain base.
  - **Faithful-lazy posture:** on lazy ([[hiveplotlib|Dask]]) edge data, subset/highlight, the narwhals-expression shorthand, *and* `hops>0` ego expansion all run without materializing the edge frame (bounded endpoint-ID-column scans only, honoring the scaling milestone's no-full-materialize invariant), and reproduce the in-memory subgraph byte-for-byte rather than approximating it (the correctness bar the scaling representation set; concrete pre-computed boolean masks and lazy node data are the stated exceptions, the latter a RAM ceiling). This is the same faithful-not-approximate discipline as [[0002-performance-regression-harness|the scaling milestone's equivalence wall]]. Deletes the four rejected `data_subset` / `data_highlight` constructor-attribute TODOs. Two new gallery notebooks: Subsetting Hive Plots, Highlighting Hive Plots.
- **`edge_coverage` introspection** (on `master`, post-0.28, unreleased): a read-only `BaseHivePlot.edge_coverage` property returning an `EdgeCoverage(drawn, total, fraction)` NamedTuple (importable from the top level) that reports how many of the underlying edges the current realization actually draws, plus a percent-only `(N% drawn)` clause in `HivePlot.__repr__`. It answers "why does my plot look like it's missing edges?" without a taxonomy of *why* each edge is undrawn: intra-axis edges without repeat axes, non-adjacent axis pairs past three axes, and overplotting all show up as a coverage below 100%. Deliberately not a warning (the repr clause is the point-of-use signal). Computed lazily behind a single representation-agnostic seam so the in-flight scaling membership-storage change is a one-spot update. `HivePlotMatrix` gets no aggregate (edges appear in multiple cells by design; per-cell coverage is reachable through each populated cell).
- **Named warning categories and a deprecation policy** (on branch `57-deprecation-policy-and-warning-categories` / MR !38, post-0.28, unreleased): warnings raised by the visualization back ends now carry named, importable categories from `hiveplotlib.exceptions` instead of plain `UserWarning`. They still subclass `UserWarning`, so existing filters keep matching, but a user can now silence one class of warning without silencing all of them (for example `ignore::hiveplotlib.exceptions.MissingPlotElementWarning` for plot-before-build warnings). This matters most for downstreams running with warnings as errors, which is how hiveplotlib's own CI runs. A companion docs page states the deprecation contract: a one-minor-version window, with every future deprecation warning through `HiveplotlibDeprecationWarning`.
- **Overlap-warning gate fix** (on branch `60-fix-overlap-warning-gate` / MR !42, post-0.28, unreleased): the [[edge-rendering|edge kwarg hierarchy]]'s overlap warning was gated backwards. It now respects the `warn_on_overlapping_kwargs` setting and names the setting being changed, and it no longer fires a false alarm when clockwise and counterclockwise edges (which never coincide, so there is nothing to override) are styled with the same keyword such as `color`. A three-file fix, but it touches the hierarchy that is the library's most-explained feature.

- **Lower the default curve resolution (`num_steps` / `num_steps_per_edge`), plan opened 2026-08-01, status *exploring*.** Every hive plot samples each quadratic Bézier edge at `num_steps` points, defaulted to 100 since the beginning; measurement puts that at roughly 4-6x more than the default 1500px canvas can resolve. Lowering it makes out-of-the-box plots build faster, render faster, and hold proportionally less curve memory, following the v0.27.0 datashader `dpi` precedent (lower default for exploration, documented escape hatch for publication output). **No code has changed and no code workstream is dispatchable**: the grill has not run, the adversary has not read the plan, and the number is deliberately unsettled. The plan recommends **50** (down from 100) on headroom grounds rather than appearance: at true standalone resolution not one pixel differs from n=100 by more than 7/255, it holds sub-quarter-pixel fidelity at a 4000px export, and it absorbs the two multipliers users legitimately turn (canvas size and `control_rho_scale`) that 25 and 16 have no margin for. The known asymmetry with the `dpi` precedent is that a user does not *see* `num_steps` change, so a publication export can go subtly polygonal with no signal, which is the main argument for the conservative number. Related: `plans/archived/adaptive-curve-sampling.md` records the measurement that produced the finding and why *adaptive* per-curve sampling was rejected in favour of a lower constant. One deferred design question, narrowed by the maintainer and explicitly not a workstream: whether the fused rasterize-from-ids path (which never persists the curves it builds) should carry its own lower default, which needs an unmeasured fused-path memory sweep first and would mean the same `HivePlot` renders at two fidelities depending on whether `construct_curves` ran. **Workstream 8 moved this plan's ground twice (2026-08-13).** It created `_DEFAULT_NUM_STEPS_PER_EDGE` as the single named home for the number, which is precisely the seam a default change needs, and a WS8 test pins `HivePlot.__init__`'s signature default equal to that constant, so a future change cannot drift the two apart silently. It also fixed the defect that three construction methods ignored `num_steps_per_edge` outright, which means a user's declared rate is now actually honored, and it shipped the render-time escape hatch on the datashader path. The plan's remaining question is narrower than when it was opened: the number itself. **Workstream 10 supplied the memory side of that decision in bytes rather than in estimate (2026-08-21):** a direct probe measured the on-instance curve representation at float32, `num_steps + 1` rows per edge, 808.0 bytes per edge at the default 100, so a candidate default's resident-memory saving is now arithmetic rather than a guess.
